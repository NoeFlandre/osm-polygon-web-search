## Goal

Create a public, Apache-2.0-licensed GitHub repository and a public, Apache-2.0-licensed Hugging Face dataset repository, both named `osm-polygon-web-search`, with a minimal local Python foundation and reproducible quality gates. The initial Hugging Face repository is metadata-only. All local and derived data remains under:

`/Volumes/Seagate M3/projects/osm-polygon-web-search`

## Scope

The first release establishes the repository and publication contracts only:

- A typed package exposes the canonical Seagate data-root path.
- A small module entry point provides a Docker smoke command that reports the configured data root without creating or reading data.
- `uv` manages the Python environment and lockfile.
- Ruff, ty, pytest, coverage, pre-commit, and mutmut provide repeatable quality checks.
- MkDocs Material provides public documentation and a GitHub Pages workflow.
- Apache-2.0 licensing and citation metadata are present in both publication surfaces.
- The Hugging Face dataset card documents the future dataset contract but contains no raw data, derived data, parquet files, PBF files, or generated artifacts.

The implementation deliberately does not include OSM scraping, PBF parsing, geospatial transformations, schema design beyond the data-root boundary, dataset generation, upload automation, model code, or cloud storage. Those are separate decisions for a later approved change.

## Data boundary

The package uses one canonical constant:

`/Volumes/Seagate M3/projects/osm-polygon-web-search`

The first implementation does not create the directory, inspect its contents, copy files from it, or accept a production override that could move data elsewhere. Tests use the path as a value only. The repository `.gitignore` protects generated development state, while the external Seagate path remains the sole location for local data.

The remote Hugging Face repository is metadata-only. Its initial contents are limited to the dataset card and Apache-2.0 license text. No local data is uploaded as part of this project.

## Repository architecture

The package stays intentionally small and deep:

```text
src/osm_polygon_web_search/
├── __init__.py       # package metadata
├── __main__.py       # minimal executable smoke entry point
└── data_root.py      # one public data-root boundary
```

The public interface is `data_root() -> pathlib.Path`. It returns the canonical path and has no filesystem side effects. `python -m osm_polygon_web_search` prints the path, making the Docker image observable without inventing application behavior.

Repository infrastructure is separated by responsibility:

- `pyproject.toml` defines package metadata, runtime requirements, development tools, Ruff, ty, pytest, coverage, and mutmut configuration.
- `uv.lock` records the reproducible environment and is generated by uv.
- `justfile` exposes the documented local quality commands without hiding their underlying tools.
- `Dockerfile` and `.dockerignore` build the package in a small Python image and run the smoke entry point.
- `.github/workflows/ci.yml` runs formatting, linting, type checking, tests, strict documentation validation, and mutation testing.
- `.github/workflows/docs.yml` builds and deploys the strict MkDocs site through GitHub Pages with least-privilege permissions.
- `README.md` is the code repository landing page; `dataset/README.md` is the separate Hugging Face dataset card.

## Documentation and legal metadata

The MkDocs site contains concise pages for:

- project purpose and current scope;
- getting started with uv and the smoke command;
- the Seagate-only data layout;
- development and the complete quality gate;
- citation and licensing.

`mkdocs.yml` uses an explicit navigation and excludes the internal `docs/superpowers/` specification directory from the published site. `LICENSE` contains the full Apache License 2.0 text. `CITATION.cff` identifies the project, author, repository, license, and initial version. The dataset card includes the Hugging Face metadata field `license: apache-2.0` and repeats the no-data publication policy.

## Test-first quality strategy

Implementation begins with `tests/test_data_root.py`:

1. Write a focused test asserting that `data_root()` returns the exact Seagate path and does not create it.
2. Run that test and record the expected RED failure because the package boundary does not yet exist.
3. Add the smallest package implementation that makes the test GREEN.
4. Add the entry-point contract test and repeat RED→GREEN.
5. Refactor only after the tests are green, without adding unrequested behavior.

The quality commands are:

```text
uv run ruff format --check .
uv run ruff check .
uv run ty check
uv run pytest --cov=osm_polygon_web_search --cov-fail-under=100
uv run mkdocs build --strict --site-dir /tmp/osm-polygon-web-search-site
uv run mutmut run
uv run mutmut results
docker build -t osm-polygon-web-search:local .
```

Mutation testing is a required signal, not a decorative dependency: the gate fails if any mutant survives or remains unresolved. The first package is intentionally small enough that the mutation run is bounded and reviewable. The final handoff reports exact command results and distinguishes incomplete or blocked runs from passing gates.

## Publication workflow

After the local repository is green and the initial commit is reviewed:

1. Create the public GitHub repository `osm-polygon-web-search` under the authenticated GitHub account and push `main`.
2. Create the public Hugging Face dataset repository `osm-polygon-web-search` under the authenticated Hugging Face account.
3. Upload only the dataset card and Apache-2.0 license to Hugging Face.
4. Configure GitHub Pages to use GitHub Actions, then monitor the documentation workflow.
5. Verify the remote commit, workflow result, live documentation response, and clean local worktree.

The GitHub and Hugging Face CLIs must be authenticated by the user. Tokens are never written to the repository or exposed in logs. If either service remains unauthenticated or unreachable, the local work is still reviewable, but publication is reported as blocked rather than inferred.

## YAGNI and future change boundary

No generalized configuration system, data registry, CLI framework, uploader, storage abstraction, geospatial dependency, or dataset schema is introduced until a concrete next requirement needs it. A future data-processing change must preserve the Seagate-only rule and receive its own RED→GREEN, documentation, and mutation-quality review.
